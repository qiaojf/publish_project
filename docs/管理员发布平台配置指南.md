# 管理员发布平台配置指南

> 适用系统：公司内部内容自动发布平台  
> 适用角色：应用管理员、发布管理员、协助配置凭证的服务器运维人员  
> 更新日期：2026-09-25

这份文档按“没有开发经验也能照着操作”的方式编写。管理员不需要理解程序代码，但需要知道：**页面中只填写非敏感信息；密码、Token、Client Secret、私钥只能放在后端服务器的环境变量中。**

当前系统支持以下发布目标：

1. 公司服务器目录（Local）
2. 公司服务器 SFTP
3. GitHub Repository
4. GitHub Pages
5. Microsoft OneDrive / SharePoint 文档库
6. Dropbox
7. Instagram Reels

快速对照：

| 发布目标 | 需要放入服务器的秘密 | 当前系统是否自动处理短期 Token |
|---|---|---|
| Local | 无 | 不涉及 |
| SFTP | 密码，或私钥及可选口令 | 不涉及；密码/密钥到期需人工轮换 |
| GitHub Repository | Personal Access Token | 否；PAT 到期需人工轮换 |
| GitHub Pages | Personal Access Token | 否；PAT 到期需人工轮换 |
| OneDrive | Client Secret | 是；每次自动申请 Access Token，但 Client Secret 到期需人工轮换 |
| Dropbox | Access Token | 否；当前版本不支持 Refresh Token 自动刷新 |
| Instagram | Access Token | 否；当前版本不支持自动刷新 |

## 1. 开始前先理解三个概念

### 1.1 发布目标

“发布目标”就是内容最后要去的位置，例如“管理部文件区”“公司 GitHub Pages”“公司 OneDrive”。管理员登录后，从左侧菜单进入：

```text
发布配置 → 新增发布目标
```

每个目标都要填写：

- 名称：给系统用户看的名称；
- 目标类型：Local、SFTP、GitHub 等；
- 支持内容类型：这个目标允许接收哪些内容；
- 平台相关字段：仓库、文件夹、账号 ID 等；
- 凭证引用：非 Local 目标用于关联服务器秘密信息的代号；
- 是否启用：关闭后不能再被新内容选择。

### 1.2 凭证引用不是密码

“凭证引用”只是一个便于识别的英文代号，不是 Token 本身。例如：

```text
github_company
onedrive_company
dropbox_company
sftp_internal
instagram_company
```

凭证引用只能使用英文字母、数字、下划线 `_` 或短横线 `-`，不能包含中文和空格。

系统会把凭证引用转换成环境变量名：

```text
PUBLISH_CREDENTIAL_{凭证引用转大写}_{凭证类型转大写}
```

例如页面填写 `github_company`，GitHub Token 对应：

```dotenv
PUBLISH_CREDENTIAL_GITHUB_COMPANY_TOKEN="实际Token"
```

页面填写 `onedrive-company` 时，短横线也会转换为下划线：

```dotenv
PUBLISH_CREDENTIAL_ONEDRIVE_COMPANY_CLIENT_SECRET="实际Client Secret"
```

### 1.3 页面字段与服务器秘密信息分开保存

下面这些内容可以填写在发布配置页面：

- GitHub Owner、Repository、Branch；
- OneDrive Tenant ID、Client ID、Drive ID；
- SFTP 服务器地址和用户名；
- 文件夹路径和 URL；
- 凭证引用。

下面这些内容绝对不能填写到页面的普通配置字段：

- 密码；
- Access Token；
- Personal Access Token；
- Client Secret；
- SSH 私钥及私钥口令；
- App Secret。

系统会主动拒绝在普通配置中保存名称包含 `token`、`password`、`secret`、`private_key`、`passphrase` 的敏感字段。

## 2. 先准备一张“资料交接表”

非 IT 管理员通常需要向公司 GitHub 管理员、Microsoft 365 管理员、服务器管理员或社交媒体负责人索取资料。可以复制下面的表格，不要在表格中记录真实密码或完整 Token：

| 项目 | 填写内容 |
|---|---|
| 发布目标名称 | 例如“管理部 OneDrive” |
| 平台负责人 | 姓名或部门 |
| 凭证引用 | 例如 `onedrive_management` |
| 凭证存放服务器 | 后端服务器 `.143` |
| 凭证类型 | Token / Client Secret / 密码 / 私钥 |
| 创建日期 | 年月日 |
| 到期日期 | 年月日；无固定日期也要填写“无固定日期” |
| 提醒日期 | 建议到期前 30 天 |
| 最近测试日期 | 年月日 |
| 最近测试结果 | 成功 / 失败 |

真实秘密只应进入公司密码管理器和后端服务器环境变量，不要放入 Excel、邮件正文、工单截图或本文件。

## 3. 如何把 Token 或密码放到服务器环境变量

### 3.1 找到正确的 `backend/.env`

凭证必须加到**后端服务器 `.143`**，不是前端服务器 `.141`，也不是本地电脑的前端 `.env`。

`.env` 实际位置：

```text
# 直接从上传项目目录运行
/home/user/tbpub_project/backend/.env
```


### 3.2 使用 MobaXterm 修改

1. 用 MobaXterm SSH 登录后端服务器 `.143`。
2. 进入实际后端目录，例如：

   ```bash
   cd /home/user/tbpub_project/backend
   ```

3. 将文件权限限制为仅当前账号可读写：

   ```bash
   chmod 600 .env
   ```

4. 打开文件：

   ```bash
   nano .env
   ```

5. 在文件末尾增加对应变量。Token 前后不要多空格，建议使用双引号：

   ```dotenv
   PUBLISH_CREDENTIAL_GITHUB_COMPANY_TOKEN="这里粘贴Token"
   ```

6. 在 nano 中按 `Ctrl+O`，按回车保存，再按 `Ctrl+X` 退出。
7. 重启后端，执行：

   ```bash
   cd /home/user/tbpub_project/backend
   source /home/user/miniconda3/bin/activate tbpub

   nohup uvicorn app.main:app \
   --host 0.0.0.0 \
   --port 8000 \
   > backend.log 2>&1 &
   ```

8. 回到系统“发布配置”页面，点击该目标的“测试连接”。


### 3.3 同名变量的优先级

如果服务启动配置中已经设置了同名环境变量，它会优先于 `backend/.env`。此时只修改 `.env` 可能仍然读取旧 Token。遇到“已经换了 Token，但系统还提示旧凭证无效”时，请部署人员检查 Supervisor、systemd 或启动脚本中的同名变量并重启进程。

### 3.4 通用轮换方法

Token、密码或 Secret 即将过期时统一按下面步骤处理：

1. 先在页面临时禁用发布目标，避免轮换期间产生失败任务。
2. 在第三方平台创建新凭证，不要立即删除旧凭证。
3. 修改后端服务器对应环境变量。
4. 重启后端服务。
5. 在页面点击“测试连接”。
6. 测试成功后重新启用目标。
7. 在第三方平台撤销旧凭证。
8. 更新凭证登记表中的到期日和提醒日。
9. 因凭证到期而失败的内容，可点击“重新发布”，不需要重新审核。

## 4. 公司服务器目录（Local）

### 4.1 适用场景

文件直接保存在后端服务器 `.143` 的指定目录，并通过 `terabox-pub.com/local-published/...` 访问。支持图片、PDF、PPT、Word、Excel、HTML、视频和普通文件等全部内容类型。

### 4.2 需要准备的资料

- 后端服务器上的发布根目录；
- 这个目录对应的访问 URL；
- 后端运行账号对目录的写入权限；
- `.143` Nginx/Caddy 对 `/local-published/` 的目录映射。

Local 不需要账号、密码、Token，也不需要填写凭证引用。

### 4.3 页面字段填写

以当前 `runtime-data` 部署为例：

| 页面字段 | 示例 | 说明 |
|---|---|---|
| 名称 | 公司内容发布区 | 用户选择发布目标时看到的名称 |
| 目标类型 | 公司服务器目录（Local） | 选择 Local |
| 支持内容类型 | 按需要多选 | 可自由组合全部类型 |
| 服务器发布根目录 | `/home/user/tbpub_project/runtime-data/published/content` | 实际写文件的目录 |
| URL 根地址 | `/local-published/content/` | 建议使用站点相对 URL |
| 是否启用 | 启用 | 测试完成后启用 |

后端环境变量必须配置公共根目录，而不是带 `content` 的目标目录：

```dotenv
LOCAL_PUBLISHED_ROOT=/home/user/tbpub_project/runtime-data/published
LOCAL_PUBLISHED_BASE_URL=/local-published
```

目录和 URL 的子路径必须一一对应：

```text
物理目录：.../published/content
URL 路径：.../local-published/content/
```

如果物理目录末尾是 `management`，URL 末尾也应是 `management`。否则系统会拒绝保存或发布，避免出现“发布成功但打开 404”。

### 4.4 到期和维护

Local 没有 Token 到期问题，但要定期检查：

- 服务器磁盘空间；
- 目录写入权限；
- Nginx/Caddy 映射；
- 域名证书；
- FortiGate 是否允许用户访问发布 URL。

## 5. 公司服务器 SFTP

### 5.1 适用场景

后端通过 SSH/SFTP 把文件上传到另一台公司服务器。全部内容类型均可使用；多文件内容会保留目录结构。

### 5.2 需要向服务器管理员准备的资料

- 服务器地址或内网域名；
- SFTP 端口，通常为 `22`；
- 专用发布用户名；
- 认证方式二选一：密码，或者 SSH 私钥；
- 私钥如果加密，还需要私钥口令；
- 远程绝对目录，例如 `/var/www/company-content/management`；
- 与远程目录对应的浏览器访问 URL；
- 服务器 SSH 主机指纹；
- 发布账号对远程目录的写入权限。

建议使用专用低权限账号，只允许写入指定发布目录，不要使用 root。

### 5.3 页面字段填写

| 页面字段 | 示例 | 说明 |
|---|---|---|
| 名称 | 公司 SFTP 发布区 | 自定义 |
| 目标类型 | 公司服务器（SFTP） | 选择 SFTP |
| 支持内容类型 | 按需要多选 | 可自由组合 |
| 服务器地址 | `192.168.1.150` | 不要填写 `http://` |
| 端口 | `22` | 以服务器管理员提供值为准 |
| 用户名 | `publisher` | 专用 SFTP 用户 |
| 远程根目录 | `/var/www/company-content/` | 必须是以 `/` 开头的绝对路径 |
| 访问 URL 根地址 | `https://content.company.example/` | 必须对应远程根目录 |
| 凭证引用 | `sftp_internal` | 仅为代号 |

### 5.4 环境变量

使用密码：

```dotenv
PUBLISH_CREDENTIAL_SFTP_INTERNAL_PASSWORD="实际SFTP密码"
```

使用私钥：

```dotenv
PUBLISH_CREDENTIAL_SFTP_INTERNAL_PRIVATE_KEY="-----BEGIN OPENSSH PRIVATE KEY-----
私钥正文
-----END OPENSSH PRIVATE KEY-----"
```

私钥还有口令时再增加：

```dotenv
PUBLISH_CREDENTIAL_SFTP_INTERNAL_PASSPHRASE="实际私钥口令"
```

密码和私钥至少配置一种。优先使用由服务器管理员管理的私钥。

系统会校验 SSH 主机密钥。第一次使用前，应由 IT 人员核对服务器指纹，并让运行后端的同一个 Linux 账号把正确主机密钥加入 `~/.ssh/known_hosts`。不要在没有核对指纹时盲目接受未知服务器。

### 5.5 到期和轮换

- 密码到期：让服务器管理员重置密码，更新 `_PASSWORD`，重启并测试。
- 私钥轮换：先把新公钥加入远程账号，再更新 `_PRIVATE_KEY` 并测试，成功后删除旧公钥。
- 私钥口令变化：同步更新 `_PASSPHRASE`。
- 服务器主机密钥变化：先确认是否为正常更换；未经确认不要删除 `known_hosts` 中的旧记录。

## 6. GitHub Repository

### 6.1 适用场景

把指定文件直接提交到 GitHub 仓库的指定目录。它是代码/文件仓库，不是网页托管服务。单文件会直接上传到仓库目录，不会额外创建内容文件夹和 `index.html`。

普通 Git 文件超过 100 MiB 时，当前系统会为 GitHub Repository 自动使用 Git LFS；GitHub 官方会阻止普通仓库中超过 100 MiB 的文件，LFS 额度和单文件上限取决于 GitHub 套餐。[GitHub 大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)

### 6.2 需要准备的资料

- 有权访问仓库的 GitHub 专用账号；
- Owner：个人用户名或组织名；
- Repository：仓库名称，不带 `.git`；
- 已存在的目标分支；
- 仓库内目标目录，例如 `published`；
- Fine-grained Personal Access Token；
- 如果组织启用了 SSO 或 Token 审批，完成组织授权/审批；
- 若会发布大文件，确认 Git LFS 存储和流量额度可用。

GitHub 推荐优先使用 Fine-grained Token，并限制到单个仓库和最小权限。[GitHub Token 创建说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

建议权限：

- Repository access：只选择实际发布仓库；
- Repository permissions → Contents：Read and write；
- Metadata：GitHub 自动提供只读；
- 如果分支有保护规则，必须允许该账号直接更新目标分支，或另建专用发布分支。

如果公司的规则暂时不能使用 Fine-grained Token，可让 GitHub 管理员评估 classic Token 的 `repo` scope，但它权限更大，不是首选。

### 6.3 创建 GitHub Token

由拥有仓库写入权限的公司 GitHub 账号操作：

1. 登录 GitHub，点击右上角头像。
2. 进入 `Settings → Developer settings`。
3. 进入 `Personal access tokens → Fine-grained tokens`。
4. 点击 `Generate new token`。
5. Token name 填写容易识别的名称，例如 `custpro-publisher`。
6. Expiration 选择公司允许的有效期，并立即登记到期日。
7. Resource owner 选择仓库所属个人或组织。
8. Repository access 选择 `Only select repositories`，只勾选目标仓库。
9. Repository permissions 中将 `Contents` 设置为 `Read and write`。
10. GitHub Pages 还要将 `Pages` 设置为 `Read-only`。
11. 点击生成并立即复制 Token；GitHub 不会长期再次显示完整 Token。
12. 如果显示 Pending，等组织管理员审批后再配置系统。

不要选择与发布无关的 Issues、Pull requests、Administration 等权限。

### 6.4 页面字段填写

| 页面字段 | 示例 | 说明 |
|---|---|---|
| 名称 | 公司 GitHub 仓库 | 自定义 |
| 目标类型 | GitHub Repository | 不要选 GitHub Pages |
| 支持内容类型 | 按需要多选 | 全部内容类型均可作为仓库文件保存 |
| Owner | `qiaojf` | 用户名或组织名 |
| Repository | `terabox_guide` | 不带 `.git` |
| Branch | `main` | 分支必须已经存在 |
| 仓库目录 | `published` | 系统当前要求填写非空目录 |
| 凭证引用 | `github_company` | 可与 Pages 共用同一 Token |

环境变量：

```dotenv
PUBLISH_CREDENTIAL_GITHUB_COMPANY_TOKEN="github_pat_开头的实际Token"
```

保存后点击“测试连接”。测试会确认仓库存在、分支存在，并检查 Token 是否有 push 权限，但不会上传测试文件。

### 6.5 Token 到期和异常处理

创建 Token 时应设置到期日并登记提醒。GitHub Token 到期后会被撤销；Token 泄露到公开仓库或长期未使用也可能被自动撤销。[GitHub Token 到期与撤销说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)

到期前：

1. 创建新的 Fine-grained Token，选择同一仓库和权限。
2. 如组织要求审批，等状态从 Pending 变为可用。
3. 替换 `_TOKEN` 环境变量并重启。
4. 点击“测试连接”。
5. 成功后删除旧 Token。

出现 403 时重点检查：Token 是否待审批、是否选错 Owner、是否遗漏仓库、Contents 是否为 Read and write、组织 SSO 是否授权、分支保护是否阻止直接更新。

## 7. GitHub Pages

### 7.1 适用场景

把静态 HTML、图片、PDF、PPT、Word 和普通文件发布成可通过 `github.io` 或自定义域名访问的站点。动态页面需要服务器运行，不能发布到 GitHub Pages。

GitHub Pages 官方不支持 Git LFS，因此当前系统会拒绝 Pages 中超过 100 MiB 的文件。此类文件请改用 GitHub Repository、Local、SFTP、OneDrive 或 Dropbox。[Git LFS 与 Pages 限制](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)

### 7.2 先在 GitHub 准备 Pages

1. 创建或选择仓库，至少先提交一个文件，使目标分支存在。
2. 打开仓库 `Settings → Pages`。
3. 在 `Build and deployment` 中选择 `Deploy from a branch`。
4. 选择要发布的分支，例如 `gh-pages`，发布目录选择 `/(root)`。
5. 保存并等待 GitHub 显示正式站点地址。

GitHub 官方只允许分支发布源使用分支根目录或 `/docs`；当前系统推荐专用 `gh-pages` 分支并选择根目录。[GitHub Pages 发布源设置](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

### 7.3 Token 权限

在 GitHub Repository 的 Token 权限基础上增加：

- Contents：Read and write；
- Pages：Read-only，用于读取 Pages 配置和最新构建状态；
- 只允许访问 Pages 对应仓库。

系统不会替管理员创建 Pages 站点；管理员必须先在 GitHub 中启用 Pages。GitHub 的 Fine-grained Token 权限表说明读取 Pages 配置和构建需要 Pages read 权限。[GitHub Fine-grained 权限表](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)

### 7.4 页面字段填写

| 页面字段 | 示例 | 说明 |
|---|---|---|
| 名称 | 公司 GitHub Pages | 自定义 |
| 目标类型 | GitHub Pages | 选择 Pages |
| 支持内容类型 | 选择静态类型 | 不要选择动态页面 |
| Owner | `qiaojf` | 用户名或组织名 |
| Repository | `terabox_guide` | Pages 仓库 |
| Pages Branch | `gh-pages` | 必须与 GitHub Pages 设置一致 |
| 仓库目录 | `content` | 内容写入的子目录 |
| Pages URL 根地址 | `https://qiaojf.github.io/terabox_guide/` | 填站点根地址，不要重复加 `content` |
| 凭证引用 | `github_company` | 可复用同一 GitHub Token |

如果 `repo_path` 是 `content`，系统会自动生成：

```text
https://qiaojf.github.io/terabox_guide/content/文件名
```

因此 Pages URL 根地址不能填写成 `https://qiaojf.github.io/terabox_guide/content/`，否则会重复目录。

环境变量与 GitHub Repository 相同：

```dotenv
PUBLISH_CREDENTIAL_GITHUB_COMPANY_TOKEN="实际Token"
```

“测试连接”会检查仓库、分支、Pages 是否已经启用，以及页面配置中的 URL 是否与 GitHub 返回的正式 URL 一致。

### 7.5 到期和维护

Token 轮换方法与 GitHub Repository 相同。除此之外还要检查：

- `Settings → Pages` 的发布分支是否被更改；
- Pages 地址或自定义域名是否变化；
- Actions/Pages 构建是否失败；
- 仓库是否被改为不支持当前套餐的可见性；
- 站点内容可能公开，禁止发布内部敏感资料。GitHub 明确提醒 Pages 站点即使来自私有仓库也可能公开可访问。[GitHub Pages 建站说明](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)

## 8. Microsoft OneDrive / SharePoint 文档库

### 8.1 适用场景

系统使用 Microsoft Entra 应用身份向指定 Drive 上传文件，不依赖某位员工保持登录。单个文件直接上传，多文件或目录内容会压缩成 ZIP。OneDrive 不是网页托管服务，因此不要把“动态页面”选为实际发布类型。

系统每次操作时会用 Client ID 和 Client Secret 自动向 Microsoft 换取短期 Access Token，管理员不需要手工维护 Access Token。真正需要轮换的是 Client Secret。

### 8.2 需要 Microsoft 365 管理员准备的资料

- 公司 Microsoft 365 / Entra 租户；
- 一个专用 App Registration；
- Tenant ID，也叫 Directory (tenant) ID；
- Client ID，也叫 Application (client) ID；
- Client Secret 的 **Value**；
- Client Secret 到期日期；
- 目标 OneDrive 或 SharePoint 文档库的 Drive ID；
- 已存在的目标文件夹路径；
- Microsoft Graph 应用权限和管理员同意。

当前适配器使用后台 Client Credentials 流程和 `/drives/{drive-id}` 文件接口。请让 Microsoft 365 管理员根据目标文档库和公司最小权限政策授予适用的 Application 权限并完成 Admin consent；当前 Graph 大文件上传会使用 upload session，官方接口权限表列出 `Sites.ReadWrite.All` 应用权限。[Microsoft Graph upload session](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)

这类权限范围较大，非 IT 管理员不要自行扩大权限；优先让 Microsoft 365 管理员评估站点级限制方案。

### 8.3 创建 Entra 应用并取得 Drive ID

以下步骤通常由 Microsoft 365 管理员完成：

1. 登录 Microsoft Entra admin center。
2. 进入 `Identity → Applications → App registrations`。
3. 点击 `New registration`，名称可填写 `custpro-content-publisher`。
4. 注册完成后，在 Overview 页面复制：
   - `Directory (tenant) ID`，用于页面 Tenant ID；
   - `Application (client) ID`，用于页面 Client ID。
5. 进入 `API permissions → Add a permission → Microsoft Graph → Application permissions`。
6. 按公司安全策略添加文件上传所需权限，然后点击 `Grant admin consent`。
7. 进入 `Certificates & secrets → Client secrets → New client secret`。
8. 创建 Secret，复制 **Value**，同时记录到期日。
9. 确认目标 OneDrive 或 SharePoint 文档库已经存在，并取得其 Drive ID。

Drive ID 是 Microsoft Graph 返回的 `drive.id`，不是站点名称、文件夹名称或浏览器地址。Microsoft 365 管理员可以使用 Graph Explorer 查询目标用户或站点的 Drive，例如：

```text
GET /users/{用户ID或邮箱}/drive
GET /sites/{site-id}/drive
```

复制响应中的 `id` 字段交给系统管理员。[Microsoft Graph Drive 说明](https://learn.microsoft.com/en-us/graph/api/drive-get?view=graph-rest-1.0)

### 8.4 创建 Client Secret 时最容易出错的地方

在 Entra 管理中心：

```text
Identity / Microsoft Entra ID
→ App registrations
→ 选择应用
→ Certificates & secrets
→ Client secrets
→ New client secret
```

创建完成后，必须复制 **Value**，不要复制 Secret ID。Value 离开页面后不会再次完整显示。Microsoft 限制 Secret 最长不超过 24 个月，并建议使用更短有效期；生产环境官方更推荐证书，但当前系统版本只实现了 Client Secret。[Microsoft 凭证管理说明](https://learn.microsoft.com/en-my/entra/identity-platform/how-to-add-credentials?tabs=client-secret)

| 支持内容类型 | 文件类内容 | 不要用于动态页面托管 |
| Tenant ID | `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` | Directory tenant ID |
| Client ID | `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` | Application client ID |
| Drive ID | Microsoft 365 管理员提供 | 不是文件夹名称 |

### 8.6 Secret 到期和轮换

建议在到期前 30 天提醒：

1. 在同一个 App Registration 中创建新的 Client Secret。
2. 立即复制新 Secret 的 Value。
3. 替换 `_CLIENT_SECRET` 环境变量并重启后端。
4. 点击“测试连接”。系统会自动用新 Secret 申请 Access Token，并读取 Drive。
5. 测试成功后再删除旧 Secret。

如果出现 `AADSTS7000222`，通常表示 Client Secret 已过期。Microsoft 官方的处理也是创建新 Secret、更新应用配置并删除旧 Secret。[Microsoft Secret 到期处理](https://learn.microsoft.com/en-us/entra/msidweb/authentication/client-secrets)

## 9. Dropbox

### 9.1 适用场景

把文件保存到 Dropbox。单个文件直接上传，多文件或目录内容会压缩成 ZIP。Dropbox 不是本系统的网页托管服务，不要用于动态页面。

### 9.2 需要准备的资料

- 公司 Dropbox 账号；
- Dropbox Developer App；
- App Folder 或 Full Dropbox 访问范围；
- 目标文件夹路径；
- Access Token；
- Token 到期时间；
- 应用权限 scopes。

建议使用 App Folder，除非确实需要访问账号中已有的其他目录。Dropbox 官方建议只申请最小范围。[Dropbox OAuth 指南](https://developers.dropbox.com/oauth-guide)

当前代码需要的权限至少包括：

- `files.content.write`：上传文件；
- `account_info.read`：执行“测试连接”时读取当前账号。

### 9.3 创建 Dropbox App 和测试 Token

由公司 Dropbox 账号操作：

1. 打开 [Dropbox App Console](https://www.dropbox.com/developers/apps)。
2. 点击 `Create app`。
3. 选择 `Scoped access`。
4. Content access 优先选择 `App folder`；只有必须写入账号其他已有目录时才选择 `Full Dropbox`。
5. 设置应用名称并创建。
6. 打开应用的 `Permissions` 页，勾选：
   - `files.content.write`；
   - `account_info.read`。
7. 保存权限设置。
8. 回到 `Settings → OAuth 2`，点击 `Generate access token` 生成本账号测试 Token。
9. 立即复制 Token，并记录平台显示或 OAuth 响应中的到期信息。

App Folder 模式下，页面中的 `/Company/Published/` 是应用专用 Dropbox 文件夹内部的路径，不是整个 Dropbox 根目录。

### 9.4 页面字段填写

| 页面字段 | 示例 | 说明 |
|---|---|---|
| 名称 | 公司 Dropbox | 自定义 |
| 目标类型 | Dropbox | 选择 Dropbox |
| 支持内容类型 | 文件类内容 | 不要用于动态页面托管 |
| 文件夹路径 | `/Company/Published/` | App Folder 模式下相对于应用目录 |
| 凭证引用 | `dropbox_company` | 自定义英文代号 |

环境变量：

```dotenv
PUBLISH_CREDENTIAL_DROPBOX_COMPANY_TOKEN="实际Dropbox Access Token"
```

“测试连接”只确认 Token 能读取当前账号信息，不会上传文件。

### 9.5 必须了解的 Token 到期限制

Dropbox 已停止为新应用创建长期 Access Token；新 Token 是短期 Token。需要长期后台访问时，Dropbox 推荐使用 Refresh Token 自动换取新 Access Token。[Dropbox 短期 Token 与 Refresh Token](https://dropbox.tech/developers/using-oauth-2-0-with-offline-access)

**当前系统版本只读取 `_TOKEN`，尚未实现 Dropbox Refresh Token 自动刷新。** 因此：

- App Console 生成的 Token 适合连接和功能测试；
- Token 到期后，系统会出现 Dropbox 认证失败；
- 管理员必须重新完成授权，取得新的 Access Token；
- 替换 `_TOKEN`，重启后端并点击“测试连接”；
- 需要长期无人值守发布时，应安排后续开发支持 App Key、App Secret 和 Refresh Token，不能假设当前短期 Token 永不过期。

Dropbox 官方说明新建应用默认使用短期 Token，后台离线访问应使用 `token_access_type=offline` 获取 Refresh Token。[Dropbox Token 迁移说明](https://dropbox.tech/developers/migrating-app-permissions-and-access-tokens)

发布成功后返回的 Dropbox 预览地址可能要求登录 Dropbox；系统不会自动创建公开共享链接。

## 10. Instagram Reels

### 10.1 适用场景和限制

当前系统通过 **Instagram API with Instagram Login** 发布 Reels：

- 只支持一个 `.mp4` 或 `.mov` 视频；
- 文件不能超过系统当前限制 1 GB；
- 标题和简介会合并成帖文说明；
- 系统会把视频临时放到公网 HTTPS 地址，让 Meta 主动下载；
- 发布结束后清理临时副本；
- 只支持 Instagram Business 或 Creator 专业账号。

Meta 的官方 Instagram API 集合列出的 Instagram Login 发布权限包括 `instagram_business_basic` 和 `instagram_business_content_publish`。[Meta 官方 Instagram API 集合](https://www.postman.com/meta/instagram/folder/1z5vxzu/instagram-api-with-instagram-login)

### 10.2 需要社交媒体负责人和 Meta 应用管理员准备的资料

- Instagram Business 或 Creator 专业账号；
- Meta for Developers 中的 Business 应用；
- 应用中的 Instagram API with Instagram Login 产品；
- `instagram_business_basic` 权限；
- `instagram_business_content_publish` 权限；
- Instagram 专业账号数字 ID；
- 能发布内容的 Instagram User Access Token；
- Token 到期时间；
- 应用当前使用的 Graph API 版本；
- 公网 HTTPS 视频暂存地址。

测试阶段，账号通常需要加入应用角色或测试范围；给公司之外的其他账号使用时，可能还需要 Meta App Review 和 Advanced Access。具体以 Meta 应用后台显示为准。

### 10.3 创建 Meta 应用和取得资料

Meta 后台菜单经常调整，以下资料建议由公司 Instagram 账号负责人和 Meta 应用管理员共同准备：

1. 先在 Instagram 中把账号确认或切换为 Business/Creator 专业账号。
2. 登录 [Meta for Developers](https://developers.facebook.com/)，进入 `My Apps → Create App`。
3. 创建公司管理的 Business 应用，不要绑定即将离职人员的个人用途应用。
4. 为应用添加 Instagram 产品，选择 Instagram API with Instagram Login 的设置方式。
5. 在 API setup 中添加要发布的专业账号，并按 Meta 提示完成账号授权。
6. 申请或启用：
   - `instagram_business_basic`；
   - `instagram_business_content_publish`。
7. 取得 Instagram 专业账号数字 ID，记录为 `ig_user_id`。
8. 生成能代表该专业账号发布内容的 User Access Token，并记录到期时间。
9. 确认应用当前使用和支持的 Graph API 版本。
10. 若应用处于 Development 模式，确认目标账号已经加入允许的角色/测试范围；正式为其他账号服务时，按 Meta 后台要求完成 App Review。

不要把 Meta App ID、Instagram 用户名或 Facebook Page ID 当成 `ig_user_id`。系统测试连接会比较 Token 返回的账号 ID 与页面填写值。

### 10.4 公网视频地址

Meta 服务器必须能直接访问视频，不能要求公司 VPN、登录、Cookie 或自定义请求头。当前域名建议填写：

```text
https://custpro.net/local-published/_instagram/
```

这个 URL 必须映射到后端：

```text
LOCAL_PUBLISHED_ROOT/_instagram/
```

FortiGate 和 `.141`、`.143` 的反向代理必须允许公网 `GET/HEAD` 访问这个临时路径。其他内部 `/local-published/` 内容仍可按公司策略限制，不要因为 Instagram 而把全部内部资料公开。

### 10.5 页面字段填写

| 页面字段 | 示例 | 说明 |
|---|---|---|
| 名称 | 公司 Instagram | 自定义 |
| 目标类型 | Instagram Reels | 选择 Instagram |
| 支持内容类型 | 视频 | 系统固定，不要混选其他类型 |
| Instagram 专业账号 ID | `17841400000000000` | 纯数字，不是 `@用户名`、App ID 或 Page ID |
| Graph API 版本 | `v23.0` | 页面当前默认值；使用 Meta 应用仍受支持的版本 |
| 视频公网 URL 根地址 | `https://custpro.net/local-published/_instagram/` | 必须公网 HTTPS 可直接下载 |
| 凭证引用 | `instagram_company` | 自定义英文代号 |

环境变量：

```dotenv
PUBLISH_CREDENTIAL_INSTAGRAM_COMPANY_ACCESS_TOKEN="实际Instagram User Access Token"
```

“测试连接”会用 Token 读取账号的 `id` 和 `username`，并确认返回 ID 与页面填写的 ID 一致。它不会上传视频，也不能证明 Meta 已经能访问临时视频 URL。

### 10.6 Token 和 API 版本到期

**当前系统只读取 `_ACCESS_TOKEN`，不会自动刷新 Instagram Token。** 请在 Meta 返回的 Token 到期日前安排轮换：

1. 由 Meta 应用管理员刷新或重新授权获得新 Token。
2. 确认新 Token 仍包含 `instagram_business_basic` 和 `instagram_business_content_publish`。
3. 替换 `_ACCESS_TOKEN` 环境变量并重启后端。
4. 点击“测试连接”。
5. 用一条无敏感信息的测试视频做真实发布。
6. 记录下一次到期日期。

Graph API 版本也有生命周期。不要因为看到新版本就直接修改；先由 Meta 应用管理员核对变更说明，在测试环境完成连接和真实视频测试，再更新页面中的版本。旧版本下线前必须完成升级。

Token 有效但发布失败时，依次检查：

- Instagram 账号是否仍为专业账号；
- 应用权限是否仍有效；
- `ig_user_id` 是否正确；
- 视频 URL 能否从公司网络之外直接打开；
- HTTPS 证书是否有效；
- 视频格式、编码、时长和大小是否符合 Meta 要求；
- Meta 应用是否仍处于允许该账号使用的模式。

## 11. 配置完成后的统一验收步骤

每新增一个发布目标，都按下面顺序验收：

1. 先保持“禁用”，填写并保存页面配置。
2. 让服务器运维人员添加对应环境变量并重启后端。
3. 回到发布配置列表，点击“测试连接”。
4. 测试成功后启用目标。
5. 建一条无敏感信息的小文件测试内容。
6. 管理员执行“保存并发布”，或走员工提交、管理员审核流程。
7. 等状态变为“发布成功”。
8. 打开发布链接，确认能看到正确文件，而不是 404、登录错误或旧内容。
9. 检查发布日志和操作日志中的平台、目标名称及错误信息。
10. 再测试接近实际业务大小的文件。

“测试连接成功”只说明账号和基本目标可访问，不等于完整发布一定成功。例如：

- Local 还要确认 URL 映射；
- SFTP 还要确认文件上传后 Web 服务器能访问；
- GitHub Pages 还要等待 Pages 构建；
- OneDrive/Dropbox 链接还受平台共享权限影响；
- Instagram 还要确认 Meta 能从公网下载视频。

## 12. 常见错误对照表

| 错误或现象 | 处理方法 |
|---|---|
| `发布目标凭证未配置：xxx/token` | 检查页面凭证引用与环境变量中间部分是否一致，修改后重启 |
| 修改 Token 后仍然报旧 Token 错误 | 检查 Supervisor/systemd 是否存在优先级更高的同名环境变量 |
| 测试连接 401 | Token/密码错误、过期或已撤销 |
| 测试连接 403 | 凭证存在，但账号或权限不足 |
| GitHub 找不到分支 | 先在 GitHub 创建并提交到该分支，页面 Branch 必须完全一致 |
| GitHub Token 无 push 权限 | Fine-grained Token 增加目标仓库的 Contents Read and write，并检查分支保护 |
| GitHub Pages URL 不一致 | 页面 Base URL 改成 GitHub `Settings → Pages` 显示的站点根地址 |
| GitHub Pages 大文件失败 | Pages 不支持 LFS，改用 Repository、Local、SFTP、OneDrive 或 Dropbox |
| OneDrive `AADSTS7000222` | Client Secret 过期，创建新 Secret Value 并轮换 |
| OneDrive 上传成功但别人打不开 | 检查 OneDrive/SharePoint 文件和站点权限；系统不自动创建匿名分享 |
| Dropbox 过一段时间后 401 | Access Token 到期；重新授权并替换 `_TOKEN` |
| SFTP 认证失败 | 检查用户名、密码/私钥、私钥口令和 `known_hosts` |
| Local 提示目录与 URL 不匹配 | 让物理目录子路径和 `/local-published/` 后的子路径保持一致 |
| Instagram 账号 ID 不一致 | 填专业账号数字 ID，不要填用户名、Page ID 或 App ID |
| Instagram 创建容器失败 | 先从外网测试视频 HTTPS URL，再检查权限和视频格式 |
| 页面显示发布成功但链接 404 | 检查 URL 根地址、反向代理映射、Pages 构建状态或文件名大小写 |

## 13. 安全和日常管理要求

- 每个平台尽量使用公司专用账号，不要绑定即将离职员工的个人账号。
- 所有 Token、Secret、密码和私钥都按密码管理，不在聊天、邮件或截图中传递完整值。
- `backend/.env` 权限保持 `600`，不上传 Git，不放到前端服务器。
- 每个平台只授予实际需要的最小权限和仓库/目录范围。
- Token 到期前设置日历提醒，建议至少提前 30 天；Instagram/Dropbox 等短期 Token 应按实际有效期提前处理。
- 员工离职、账号权限变化、怀疑泄露时，立即禁用发布目标并撤销凭证。
- 轮换时先验证新凭证，再撤销旧凭证，避免发布中断。
- 每月点击一次“测试连接”，并做一次小文件真实发布。
- 每季度核对发布目标列表，禁用不再使用的目标。
- 环境变量只保存实际秘密，不要把账号名、路径、到期日混在变量值中。
